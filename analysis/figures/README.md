# Figures

Generated by `python scripts/make_figures.py` from `results/`. Figures are PNG at 300 dpi. Widths match IEEEtran conference: `fp32_teachers_*` and
`qat_precision*` are text width (`figure*`, 7.16 in); the others are column width (3.5 in).
The numbers behind each plot are in `data/`.

## Shared encoding

| Channel | Meaning |
| --- | --- |
| Colour (blue / orange / green) | Input size 160 / 192 / 224 px |
| Solid vs hatched bar; filled vs hollow marker | Architecture: **Base** vs **Slim** |
| Marker shape (circle / triangle) | Bit-width: 6-bit / 8-bit (weights and activations) |
| Full vs light colour | Teacher: **TA** (ResNet18 teacher assistant) vs **Direct** (ResNet50), only in `fp32_teachers_*` |

**Base** is `test_resnet.r160_in1k` (373k parameters); **Slim** is Base with the last two stages
narrowed to 128 and 64 channels (218k parameters). "8-bit"/"6-bit"/"4-bit" means 8w8a/6w6a/4w4a QAT.

## Captions

**`fp32_teachers_accuracy`** (also `_f1_weighted`)
> Full-precision test accuracy of each student and input size, distilled from the ResNet18
> teacher assistant (full colour) or directly from ResNet50 (light). Bars: mean of 5 seeds;
> whiskers: 95% t interval. Each seed draws a different patient split. The y-axis starts at 60%.

**`qat_precision_accuracy`** (also `_f1_weighted`)
> Test accuracy after quantization-aware training at 8 and 6 bits, next to the FP32 starting
> point, for students distilled through the ResNet18 teacher assistant. Bars: mean of 5 seeds, value
> on top; whiskers: 95% t interval.
> Each QAT run starts from the FP32 checkpoint with the same seed, split, student and teacher.
> The y-axis starts at 70%. 4-bit (57.3–62.2%) is shown in `qat_precision_with_4bit_*`.

**`qat_precision_with_4bit_accuracy`** (also `_f1_weighted`)
> As above, including 4-bit QAT; the y-axis starts at 50%.

**`u250_accuracy_vs_throughput`**
> Mean QAT test accuracy (TA teacher, 5 seeds) against the maximum throughput of each configuration on
> the Alveo U250 (FINN dataflow accelerator at 100 MHz; all 12 builds meet timing, so these are the
> on-board rates). Throughput depends only on input size: the first layer takes one input pixel per
> clock, so the limit is 100 MHz / (H+2)² = 3,810, 2,657 and 1,958 FPS at 160, 192 and 224 px, for both
> architectures and bit-widths. Each build reaches this limit with the least parallelism FINN finds for
> it (minimum-area builds, see notes). The y-axis spans 79–83.5%.

**`u250_accuracy_vs_area`**
> Mean QAT test accuracy against the LUT (left) and BRAM (right) use of the same minimum-area builds, as %
> of the U250 (post-synthesis, including the platform shell). At equal throughput, bit-width sets most of
> the area: 8-bit needs ~1.8 points more LUTs and 1.5–1.7× the BRAM of 6-bit, while Slim saves ~0.4 LUT points
> and 12–19% BRAM over Base. DSPs are not shown: every Base build uses 2,817 and every Slim build 2,573,
> at all input sizes.

**`u250_slim160_6bit_area_vs_throughput`**
> U250 resources (post-synthesis, % of the device) used by Slim, 160 px, 6-bit, built for
> increasing throughput with stock FINN folding. From 108 to 3,810 FPS (35×) LUTs grow 1.8× and DSPs 45×;
> most LUT, FF and BRAM use is independent of throughput. BRAM counts an 18K block as half a 36K block.

## Notes for the text

- QAT belongs to the teacher-assistant pipeline, so all QAT figures use the ResNet18-TA runs only.
  The sweep also ran QAT on the ResNet50-direct students; those runs stay in `results/qat_sweep` and
  `data/summary.csv` but are not plotted. The TA-vs-direct comparison is the FP32 figure.
- Paired QAT − FP32 change (TA runs; same seed, split and student; `data/paired_change_vs_fp32.csv`),
  30 pairs per bit-width: 8-bit −0.7 pp [−1.7, +0.3], 6-bit −1.5 pp [−2.3, −0.6], 4-bit −23.3 pp [−24.7, −21.9].
- TA minus direct at FP32: Base +2.2 / −1.8 / −2.6 pp and Slim +0.6 / +1.8 / −1.0 pp at 160 / 192 / 224 px.
  TA tends to help the weaker settings (smallest input, Slim at 192), but every interval overlaps.

- Teacher, input size and architecture differences are within the seed-to-seed spread
  (SD 2–4 pp on 133 test images); the figures do not support ranking them.
- Minimum-area builds (`flow = relaxed_swu_patch` in `results/hw/builds.csv`): FINN two-pass relaxation
  (first fold for a 10,000 FPS target, then refold every layer to the cycles of the slowest one) plus a
  local fix to FINN's `SetFolding`: the window generator in front of a max-pool copies the pool's
  parallelism without checking its own cycles, which left every network at ~80% of its limit. Only
  pool folding changes; all compute layers keep the relaxed folding. All 12 meet 100 MHz with margin
  (Vitis reports 103.6–121.4 MHz achievable); the kernel clock stays at 100 MHz.
- With minimum-area folding, area hardly depends on input size: every Base build uses 2,817 DSPs and
  every Slim build 2,573; LUTs are 13–16% of the device (post-synthesis, including the platform shell's
  ~57k fixed LUTs). The earlier builds that reach the same throughput with stock folding (`flow = stock`,
  targets 2,000–5,300 FPS) use 37–64% more DSPs and 18–42% more non-shell LUTs; they are kept as the
  over-provisioned comparison and are not plotted.
- The plotted builds use the QAT sweep checkpoints (seed 42, TA teacher) with the black-border trim
  at every input size. Throughput and area do not depend on the trained weights, so
  `u250_accuracy_vs_throughput` pairs each build with the 5-seed sweep accuracy of its configuration.
  Some stock builds (Base 224 `test_resnet_{6w6a,8w8a}`) came from earlier untrimmed checkpoints; the
  trim is a host-side crop, so their hardware is the same as a trimmed build's.
- All 240 sweep runs use the black-border trim at every input size. Slim reports do not record
  `student_preprocess`, but the slim scripts apply `trim_fundus_black_border` to all splits.
- Intervals are nominal: seeds share one dataset and their test splits can overlap.
